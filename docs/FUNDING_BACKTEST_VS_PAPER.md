## 1. Как устроен фандинг в каждом контуре (по коду)

### 1.1 Live/paper: расчётное начисление, непрерывная аппроксимация

Ставка берётся живая с биржи либо дефолт 0.01% за 8ч
(`astra_bot/decision/broker.py:136-137` конструктора):

```python
        funding_rate: Decimal = Decimal("0.0001"),
        funding_interval_hours: Decimal = Decimal("8"),
```

Число интервалов — pro-rata по времени удержания
(`astra_bot/decision/broker.py:714-729`):

```python
    def _funding_intervals(self, pos: PaperPosition) -> Decimal:
        """Сколько интервалов фандинга прожила позиция (pro-rata).

        Время — детерминированное: bars_held × длительность timeframe.
        Реальная биржа списывает фандинг дискретно 3 раза в сутки
        (00:00/08:00/16:00 UTC+8 по открытым позициям); здесь —
        пропорциональная аппроксимация, честная в среднем и
        детерминированная при реплее.
        """
        minutes = _TIMEFRAME_MINUTES.get(getattr(pos, "timeframe", "") or "", 60)
        held_minutes = Decimal(pos.bars_held) * Decimal(minutes)
        interval_minutes = self.funding_interval_hours * Decimal("60")
```

Начисление при КАЖДОМ закрытии, на нотионал
(`astra_bot/decision/broker.py:730-753`):

```python
        payment = fill * qty * rate * intervals
        if pos.direction in ("short", "sell"):
            return -payment
        return payment
```

### 1.2 Бэктестер: фандинга НЕТ вообще

В `astra_bot/backtester/` нет ни одного упоминания funding (grep по
каталогу — 0 вхождений). Издержки бэктестера — только комиссии 0.1% на
вход (`astra_bot/backtester/engine.py:59-65`) и slippage 0.1% на вход
(`engine.py:458-459`):

```python
        notional = quantity * entry_price
        fees = notional * self.config.maker_fee_rate
        slippage = notional * self.config.slippage_percent
        effective_price = entry_price + slippage / quantity
```

То есть «своя модель» бэктестера = нулевой фандинг. Это и есть
расхождение: backtest-результат систематически ЛУЧШЕ live на величину
фандинга.

## 2. Замер влияния на существующие результаты

`/tmp/venv/bin/python scripts/measure_funding_impact.py models/paper_trades.jsonl`:

```
файл: models/paper_trades.jsonl
сделок: всего=122 закрыто=122 открыто=0
net PnL (закрытые): -1761.45
комиссии: 421.09
фандинг (+ заплатили / - получили): 2.51
фандинг как % от |net PnL|: 0.14%
удержание, часов: медиана=0.42 среднее=0.85 макс=8.86
сделок короче интервала фандинга (8ч): 117/122
```

Выводы из цифр:

1. Фандинг — 2.51 USDT за 122 сделки при комиссиях 421.09: **0.6% от
   объёма комиссий** и 0.14% от |net PnL|. На три отчётных дня влияние
   пренебрежимо.
2. Причина малости — короткие удержания: медиана 25 минут, 117 из 122
   сделок живут МЕНЬШЕ 8-часового интервала; pro-rata начисляет им
   доли интервала.
3. Второй порядок расхождения: live-аппроксимация непрерывная, биржа
   списывает дискретно 3 раза в сутки. Сделка, пересёкшая метку
   начисления, платит полный интервал, где pro-rata взял бы долю.
   Отклонение на сделку ≤ 1 интервала = ≤ 0.01% нотионала при ставке
   0.01% — на медианных нотионалах ~3.4k USDT это ≤ 0.35 USDT/сделка
   в худшем случае, на практике меньше.

## 3. Решение (B11)

**Зафиксировать расхождение документально; дискретные начисления в
обоих контурах НЕ внедрять.** Основания:

1. Замер (§2) показывает влияние на два порядка меньше, чем у
   комиссионной разницы контуров (421 USDT комиссий против 2.51 USDT
   фандинга). Сначала разумнее выровнять комиссии бэктестера с live
   (0.1% вход-only против 0.05% обе стороны + slippage обе стороны —
   см. docs/BACKTEST_VS_PAPER_SEMANTICS.md §3), это даёт на порядки
   больший эффект на сравнимость.
2. Дискретная схема (списание в фиксированные метки 00/08/16 UTC+8 по
   позиции, открытой на метку) в live-брокере сделало бы начисление
   ЗАВИСИМЫМ от времени сессии CI (процесс живёт 200 секунд каждые
   5 минут): сделка, закрытая в той же сессии, что и открытие, вообще
   не доживала бы до метки — это менее честно, чем текущий pro-rata
   по фактическому времени удержания. Текущая live-модель менять не
   должна.
3. Если в блоке C появится регулярное сравнение backtest↔paper на
   длинных горизонтах — добавить в бэктестер дискретные начисления по
   меткам (тот же график 00/08/16 UTC+8) отдельным PR с прогоном
   «до/после» на существующих прогонах.
