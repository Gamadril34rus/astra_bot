# Метод «Зевс» в боте: сверка, гейты входа, телеметрия

Документ описывает, что из методики внешнего автора реально механизировано, как
включается гейт «не торгуй в шуме» и какие поля теперь всегда есть у сделки.
Человеческая сводка «тезис → код → статус» — в
`reports/zeus_method_vs_bot_2026-09-14.md`; здесь — спецификация, применимая без
контекста переписки.

## 1. Гейты входа `entry_gates`

Модуль: `astra_bot/decision/entry_gates.py`. Хук: `TradingEngine.process_symbol`,
сразу после того, как meta-слой выдал кандидат и risk-контур его разрешил (т.е.
гейт режет именно *вход*, а не оценку).

Два правила, оба — из уже измеренного, новых порогов по вкусу не заводили:

| Гейт | Правило | Источник решения |
|---|---|---|
| A `REGIME` | не входить, пока режим = `LOW_VOLATILITY` | на наших 180 сделках 89 % trades прошли в LOW_VOLATILITY со средним R −0.275; regime 2.0 уже считает ось волатильности, «OFF» для неё никто не просил |
| B `COSTS_R` | не входить, если ожидаемый round-trip стоит ≥ `entry_gate_max_costs_r` долей R | издержки цикла ≈ 30.1 б.п. нотионала ⇒ `costs_r ≈ 0.301 % / стоп%`; при стопах 1.1–1.6 % это 0.19–0.27 R, при структурных 4h-стопах метода — 0.08–0.15 R |

Формула B (общая с notes-снимком движка, чтобы не было «двух правд»):

```
costs_r = 2 · (fee_pct + slippage_pct) / (|entry − stop| / entry)
```

Ключи конфигурации (`TradingEngineConfig`, `astra_bot/decision/trading_engine.py`):

| Ключ | Дефолт | Значение |
|---|---|---|
| `entry_gates_enabled` | `False` | живой режим: блокирует вход. **Выключен намеренно** |
| `entry_gates_shadow_enabled` | `True` | тень: считает и пишет наблюдение, вход не трогает |
| `entry_gate_block_regimes` | `frozenset({"LOW_VOLATILITY"})` | список режимов гейта A |
| `entry_gate_max_costs_r` | `0.25` | порог гейта B; `0` = «дорогой любой вход» |

Семантика:

* `blocked = True, live = False` (тень) → только счётчик + наблюдение;
* `blocked = True, live = True` (живой) → `return` до сайзинга, вход снят;
* исключение внутри гейта = **fail-open** (сломать торговлю гейт не может);
* при `enabled=False, shadow_enabled=False` `costs_r` даже не считается.

Наблюдаемые артефакты одного срабатывания:

* лог-строка с ключевым словом `ENTRY_GATE` (`... SHADOW BTC-USDT gate=COSTS_R costs_r=0.312 ...`);
* метрика Prometheus `ENTRY_GATE_TOTAL{gate,mode}` (`mode` = `live`/`shadow`);
* `eng.entry_gate_stats["COSTS_R:shadow"]` — счётчик в памяти;
* запись в `models/no_trade_observations.jsonl` с `rejection_stage="entry_gate"`,
  `reason_code="ENTRY_GATE_<КОД>"` и полем `hypothetic_r` в исходе.

### 1.1 Гипотетический R

`astra_bot/ml/no_trade_observations.py::_hypothetic_r` — «чем бы это
закончилось», если бы вход не отклонили. Правила зафиксированы:

* отсчёт от `close` сигнального бара (тот же репер, что у горизонтов);
* R = `|entry − stop|` кандидата, направление — из `candidate["direction"]`;
* касание стопа приоритетнее касания тейка **в одном баре** (консервативно);
* уровень исполняется ровно на цене уровня (без гэпа);
* нет касания за `max(DEFAULT_HORIZONS) = 24` бара → выход по `close`,
  `incomplete=True`, если баров будущего ещё не хватает;
* **gross**: комиссии не вычитаются (иначе «до/после» было бы не с чем сравнить);
* геометрия непригодна (стоп = вход, нет цены) → `None`, молча.

Пишется в `_outcomes[id]["hypothetic_r"]` и аддитивно переносится в JSONL-строку
наблюдения. Ничего из этого не влияет на решение.

### 1.2 Порядок включения (решение владельца)

1. Смотреть тень ≥ 7 дней: `ENTRY_GATE_TOTAL` по `gate`, долю отклонённых
   кандидатов и распределение `hypothetic_r` (медиана, доля ≤ −1R).
2. Считать гейт полезным только если `median(hypothetic_r) < 0` у отклонённых —
   иначе он режет не шум, а прибыль.
3. Включение — одной строкой конфига `entry_gates_enabled: true` (или через
   `ASTRA_*`-переменную окружения), откат — обнулением флага. Пороги при
   включении не двигать: сначала измеряем ровно ту конфигурацию, которая
   задокументирована.

Ожидаемый эффект на историческом срезе (лабораторные прогоны В3–В5, не
обещание): база −2 121.01 U → `costs_r<0.25` +128.71 U (n=31), стек «только 1h
+ без V:LOW + costs_r» −290.87 U (n=26). Это оценка *на закрытых сделках*, не
контрфактический прогноз.

## 2. Телеметрия входа (всегда включена)

Раньше поля entry-телеметрии зависели от доброй воли вызывающего: движок их
писал, а любой вход в обход движка — нет (132 из 180 записей эпохи-2 пришли без
`effective_entry`/`initial_stop`, и декомпозиция P&L на них слепая).

`PaperBroker.open_position` теперь сам дописывает в `pos.notes` (значения из
переданных `notes` имеют приоритет, `setdefault`):

| Поле | Источник |
|---|---|
| `signal_bar_close` | `entry_price` аргумент (close сигнального бара) |
| `effective_entry` | фи́лл после слиппеджа, который считает сам брокер |
| `initial_stop` / `initial_take` | аргументы `stop_loss` / первый уровень тейка |
| `stop_pct` | `|entry − stop| / entry` |
| `costs_r` | та же формула, что в §1 |

`mfe_r`/`mae_r` у позиции, закрытой до первого обновления цены, равны 0 **по
построению** (`_r_metrics` на пустой ценовой истории отдаёт `0.0`). Экстремумы
`highest_price`/`lowest_price` при этом намеренно НЕ инициализируются: `exit_plan`
использует их как ценовую историю позиции (правило D1-structural), и посев ценой
входа менял бы решения по выходам — а эта часть обязана быть чистой телеметрией.
`_r_metrics` восстанавливает риск из `notes["initial_stop"]`, если
`risk_distance` не заполнен; `_entry_snapshot` для старых позиций берёт
`effective_entry` из `fill_price` и `initial_stop` из `entry ± risk_distance` —
ничего не изобретая (`signal_bar_close` знает только движок, поэтому у legacy
он остаётся `None`).

Ledger-событие фи́лла на открытии (`kind="fill"`, `meta.phase="open"`) содержит:
`signal_bar_close`, `fill_price`, `slippage_realized_pct`, `slippage_model_pct`,
`fee_model_pct`. **Знак** `slippage_realized_pct` — «положительное = против
нас». В paper realized ≡ model: своего фи́лла у нас нет, `place_order` не
реализован. Поле заведено сейчас, чтобы с приходом биржевого фи́лла оно стало
измерением модели 0.1 %/сторону, а не новой правкой.

## 3. Кэш реальных баров

`astra_bot/data/klines_cache.py` → `models/klines_cache/{SYMBOL}_{TF}.jsonl`
(append-only, строка `{"t","o","h","l","c","v"}` на бар, `t` — `open_time`).

* пишется из `TradingEngine.fetch_context` после сборки контекста — один `try`
  на весь вызов, исключение кэша не влияет на торговлю;
* только закрытые бары (`close_time <= now`, единицы `open_time` определяются по
  порядку величины, сравнение — в тех же единицах);
* дедуп по хвосту: повторный вызов на том же окне не дописывает ничего; после
  рестарта последняя строка читается с диска, так что дублей нет и там;
* `klines_cache_keep_days` (45) — ротация раз в `prune_every_writes` записей;
* состав ТФ — `klines_cache_timeframes` (default `5m`), `enabled=False` —
  тихий no-op.

Зачем: склейки из `no_trade_outcomes` (медиана 31 бар) не позволяют мерить
мультисуточные горизонты и пересобирать реплеи по истечении окна; кэш даёт
полную историю реальных баров с этого момента.

## 4. Реплей-реванш (`scripts/track_c_replay.py`)

Правила фиксируются **до** прогона; подгонка под OOS = провал задания.
`strong` как метка силы запрещена (PR #77: много гипотез на одном OOS-срезе),
допустимы `moderate` / `weak` / `none`.

| Вариант | Правило | Базлайн |
|---|---|---|
| Z3 | ложный пробой границы канала + закрытие обратно внутрь → контр-вход, стоп за экстремумом фейка, цель — противоположная граница | пробой границы |
| Z4 | overshoot: 3-й экстремум с перехаем/перелётом уровня и закрытием обратно | пробой шеи тройной фигуры |
| Z6 | Z1 (ретест-вход разворота) **и** согласие дневной ленты EMA 20/50/100/200 (`astra_bot/decision/htf_gates.ribbon_bias`, текущий незакрытый день исключён) | та же Z1 без контекста |
| Z7 | вход у границы зоны только по первому закрытию в сторону входа после касания (`Z7_MIN_TOUCHES=2`, окно реакции `Z7_REACTION_BARS=6`) | Z5 (вход от границы без требования реакции) |

Запуск на официальных архивах `data.binance.vision`:

```bash
python scripts/track_c_replay.py \
  --source binance-vision --archive-dir /data/binance \
  --years 2021,2022,2023,2024,2025 \
  --provenance "data.binance.vision spot klines monthly, sha256 in README" \
  > reports/track_c_zeus_official_$(date +%F).md
```

Загрузчик ищет `**/{SYMBOL}USDT-{TF}-YYYY-MM.(csv|zip)` в любой вложенности
(`klines/spot/BTCUSDT/1h/monthly/…` или плоский каталог), сам определяет
заголовок (его нет в файлах до 2025-01), приводит `open_time` из мс к секундам,
склеивает файлы, дедуплицирует по `open_time`.

**Статус: ждёт данных.** Официальных CSV в репозитории нет, REST Binance из
рабочей среды недоступен. До прихода данных проверяется механика:

```bash
python scripts/track_c_replay.py --self-test   # 10 проверок, ~18 с
```

Важное ожидание: Z6 не измерима на коротком окне — дневной ленте нужно ≥ 200
закрытых дневных баров; на 41–166-дневном фиде PR #77 она даёт ноль сигналов.
Ноль из-за отсутствия контекста ≠ опровергнуто: скрипт печатает
`htf_context_coverage` (долю баров с определённым смещением), чтобы эти два
случая не путались.

## 5. Что здесь НЕ делаем

* `place_order/cancel_order/get_positions` — не реализуем (этот PR не про live).
* `vol_expansion_ratio`, уровни тейков/стопов, ML-фильтры, модель издержек —
  не трогаем.
* Расширенный cooldown и выключение 5m-ноги — решения торгового среза, не PR.
* Живым дефолтом гейты не включаем до среза ~26–27.09 (окно фиксации #76).
