## 1. Гейты

### (а) Shadow-гейт

Окно наблюдения: **08.10 → 22.10**. Все условия одновременно:

- сделок ≥ 50;
- expectancy ≥ +0.10 R;
- profit factor ≥ 1.15;
- P ≥ 80%.

«P» = winrate: доля прибыльных сделок в окне тени ≥ 80%. Считается по тем же
сделкам, что и expectancy и PF.

Источник данных: тень-гейт входа (`entry_gates_shadow_enabled=True`), см.
`docs/ZEUS_RECONCILIATION.md` §1: лог-ключ `ENTRY_GATE`, метрика
`ENTRY_GATE_TOTAL{mode="shadow"}`, журнал `models/no_trade_observations.jsonl`.

Результат: _заполняется по итогам окна_.

### (б) Сверка учёта: деньги vs R

Денежный P&L по бирже должен сходиться с суммой R по журналу сделок.

- «В7» — гейт арбитра, **вне репозитория**. Сверка «деньги vs R» за окно
  наблюдения: расхождение учёта R и долларовой записи должно быть в допуске.
  Критерий и допуск — вне репозитория (гейт арбитра).

Результат: _не выполнено_.

### (в) VST-demo прогон

Все пункты обязательны:

- ≥ 30 циклов вход/выход на VST;
- reject и partial обработаны. Сейчас `LiveBroker.open_with_protection` **не
  проверяет** `status` entry-ордера (см. аудит в описании PR);
- рестарт процесса при открытой позиции: после рестарта состояние восстанавливается
  с биржи. Сейчас `LiveBroker.reconcile` только считает `missing_stops` и
  **не восстанавливает** стоп (см. аудит);
- кнопки `/stop` и `/flat` работают end-to-end: Telegram → запись в
  `models/zeus_live_commands.json` → `apply_pending` (`astra_bot/decision/live_commands.py`)
  → `LiveBroker` → биржа.

Результат: _не выполнено_.

### (г) Слип-коридоры реала против paper-модели

Фактический слип реальных fill сравнивается с paper-моделью издержек
(см. `docs/COST_MODEL.md`):

- p50 ≤ 1.25×;
- p90 ≤ 1.5×;
- p95 ≤ 1.8×.

Цикличность гейта (г) **сознательна**: до $100 слип меряется **канарейкой
$100** (это её задача), после — сверка с коридорами.
Измеряется на канарейке после гейта тени.

Результат: _не выполнено_.

### (д) Arm-флаг

Требование: торговля выключена по умолчанию; включение — отдельный PR и явное
слово владельца.

Состояние кода на дату фиксации:

- отдельного **торгового** arm-флага в коде нет;
- `ZEUS_LIVE=1` включает только наблюдательный тик `scripts/zeus_live_clock.py`:
  он делает `reconcile` и применяет команды, а сигнал→вход не подключён
  (в логе: `signal→entry hook not armed in phase-1 (observe)`);
- `zeus-live-clock.yml` — только ручной запуск, `dry=true` по умолчанию.

Вывод: по умолчанию торговли нет (условие выполнено), но сам флаг, который
включал бы вход, ещё не создан. Его создание — отдельная задача и отдельный PR.

Результат: _частично_.

## 2. Переменные ZEUS_* (см. `.env.example`)

Примеры переменных `ZEUS_LIVE`, `ZEUS_VST`, `ZEUS_MAINNET` закомментированы в
`.env.example` намеренно: раскомментирование — осознанное действие владельца.
Фактическое поведение (по коду):

- `ZEUS_LIVE=1` без `ENVIRONMENT=live` → ABORT; `ENVIRONMENT=live` без `ZEUS_LIVE=1` → ABORT;
- `ZEUS_VST` по умолчанию `1`;
- `ZEUS_MAINNET=1` при `ZEUS_VST` в (`1`,`true`,`yes`) → ABORT (`zeus_live_clock._guard`);
- `ZEUS_MAINNET=1` без явного `ZEUS_VST=0` → клиент остаётся на VST
  (`live_env.resolve_base_url`), то есть для mainnet нужен явный `ZEUS_VST=0`.

## 3. Пульсатор: внешний запуск тика

### 3.0 Факты

- `zeus-paper-clock.yml`: `schedule: */5` и `workflow_dispatch`. README описывает
  внешний пинок через cron-job.org → `workflow_dispatch`.
- `zeus-live-clock.yml`: **только** ручной запуск. Пульс для live не нужен.
- Нативный `schedule` ненадёжен: best-effort, задержки и пропуски тиков. В
  **public**-репозитории GitHub автоматически отключает scheduled-workflow после
  60 дней без активности репозитория. `workflow_dispatch` этим не отключается,
  поэтому внешний пинок — основной механизм, нативный `schedule` — запасной.
- Строку `pulse: external ok` в код **не добавляем**. Проверка внешнего пинка —
  появление нового запуска в списке Actions сразу после пинка (событие
  `workflow_dispatch`).
- Ограничение арены: `.github/workflows/**` арена пушить не может (права App).
  **Любые** правки workflow, включая `repository_dispatch`, делает владелец.

### 3.1 Вариант 1: cron-job.org → workflow_dispatch

Как работает: cron-job.org делает `POST`
`https://api.github.com/repos/Gamadril34rus/astra_bot/actions/workflows/zeus-paper-clock.yml/dispatches`
с телом `{"ref":"master"}` и заголовками `Authorization: Bearer <token>`,
`Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`.

Важно: секрет **в URL** для GitHub API не работает — токен передаётся в заголовке.
Схема «secret в URL» потребовала бы промежуточного relay, который тоже держит
токен; это вне рамок этого PR.

Что засекретить: один fine-grained PAT (только этот репозиторий, право
**Actions: Read and write**, при 403 дополнительно Contents: read). Токен живёт
только в cron-job.org.

Чек-лист владельца (~5 мин):

1. GitHub → Settings → Developer settings → Fine-grained tokens → новый токен:
   репозиторий `astra_bot`, Actions: write, срок ≤ 90 дней. Записать дату истечения.
2. cron-job.org → New cron job: URL из выше; method `POST`; body
   `{"ref":"master"}`; три заголовка; расписание `*/5` мин.
3. Токен — только в поле заголовка cron-job.org. Не в репо, не в чат, не в `.env.example`.
4. Включить уведомления cron-job.org о падении job (non-2xx).

Verify-сценарий:

1. Ручной запуск job в cron-job.org («Run now») → HTTP 204.
2. В Actions в течение ~1 мин появился run `zeus-paper-clock` с
   `event=workflow_dispatch`.
3. Запуск в списке Actions появился сразу после пинка (в пределах минуты), а не
   по расписанию. Строку `pulse: external ok` в код не добавляем (см. 3.0).

Риски: истечение токена → тихая остановка пинков. Нужен отдельный контроль:
«последний run старше 15 мин» (в Actions или в мониторинге).

### 3.2 Вариант 2: токен/App → repository_dispatch

Как работает: `POST /repos/Gamadril34rus/astra_bot/dispatches` с телом
`{"event_type":"zeus_pulse"}`.

Требует **правки workflow** `zeus-paper-clock.yml`: добавить триггер
`repository_dispatch: types: [zeus_pulse]`. Эту правку делает владелец.

Что засекретить: токен того же класса, но для dispatches нужен **Contents: write**
(проверить по актуальной документации GitHub). Это шире, чем Actions: write:
утёкший токен может писать в репозиторий.

Чек-лист владельца: токен (как в 3.1, но Contents: write), правка workflow
владельцем, cron-job.org job с другим URL и телом, уведомления о падении.

Verify-сценарий: тот же, что в 3.1.

### 3.3 Рекомендация

**Рекомендация: вариант 1 (cron-job.org → workflow_dispatch) — принято арбитром.**
Причины:

- не требует правок workflow — `workflow_dispatch` уже есть, и README уже описывает эту схему;
- токен с Actions: write, а не Contents: write, — меньший радиус поражения при утечке;
- не зависит от того, что `schedule` может быть отключён.

Вариант 2 имеет смысл только если понадобится пинать несколько workflow или
передавать payload. Нативный `schedule` оставить запасным.
